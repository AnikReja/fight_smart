# FightSmart local API

Optional FastAPI + SQLite server that turns the browser app's per-video tags into a **library**: sessions holding
several videos, stored in one database file instead of only in browser storage. It runs on your computer;
nothing is sent anywhere, and video files are never stored, only their tags, rounds, and combo decisions.

The app works without it ("Browser only" in the top bar) and switches to "Library" when it is running.

## Run

```bash
cd server
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m uvicorn fightsmart_api.main:create_app --factory --port 8000
```

Or from the project root after setup: `npm.cmd run api`. Then start the app (`npm.cmd run dev`); Vite forwards
`/api` to port 8000. Interactive API docs: http://127.0.0.1:8000/docs (generated by FastAPI).

Data lives in `server/data/fightsmart.db` (git-ignored). Set `FIGHTSMART_DB` to use another file.

## Data model

```
sessions (id, name, date, kind: sparring|scouting, opponent, notes)
   │ 1
   │ *
videos   (id, session_id → sessions ON DELETE SET NULL, file_name, size, last_modified, duration)
   │ 1                                   └── UNIQUE(file_name, size, last_modified) = the browser's fingerprint
   ├──* tags    (video_id, id, time, label, note, fighter, outcome)   PK(video_id, id), index (video_id, time)
   ├──* rounds  (video_id, id, start, end)
   └──* reviews (video_id, combo_id, status: confirmed|rejected)
```

- **Fingerprint, not path:** browsers never reveal a file's path, so a video is identified by name + size +
  modified time, the same key the app already used for browser storage.
- **Per-video ids:** tag ids come from the browser and are only unique within a video, so the primary key is
  `(video_id, id)`.
- **Deleting a session keeps its videos** (`ON DELETE SET NULL`); deleting a video removes its tags (`CASCADE`).
- **Constraints in two places:** Pydantic rejects bad requests with a 422 before SQL runs; `CHECK` constraints in
  SQLite guard the data even if something bypasses the API.

## API

| Method | Path | |
|---|---|---|
| GET | `/api/health` | Is the server up? |
| GET / POST | `/api/sessions` | List (with video and tag counts) / create |
| GET / PATCH / DELETE | `/api/sessions/{id}` | One session with its videos / edit / delete |
| POST | `/api/videos` | Register by fingerprint; **idempotent** (returns the existing video) |
| GET | `/api/videos?session_id=` | List videos |
| PATCH | `/api/videos/{id}` | File into a session (`session_id`) or unfile (`clear_session`) |
| GET / PUT | `/api/videos/{id}/data` | Tags, rounds, combo decisions; PUT replaces them in **one transaction** |

## How the app syncs

1. Opening a video: register it, fetch its data, and **reconcile** with the browser's copy
   (`src/lib/sync.ts`): drop anything this browser deleted; then one side empty → use the other; both have data → merge without deleting, the browser
   wins on the same id; upload only if the result differs.
2. Every edit: saved to browser storage immediately, and to the server **debounced** 0.7 s after the last change
   (a burst of tags becomes one request).
3. Server down: the top bar shows "Sync error" or "Browser only"; nothing is lost because browser storage is
   always written first. Reopening the video later merges the missed edits back.

Deletions: a merge on its own can't tell "deleted in this browser" from "added somewhere else", so the browser keeps a
small record of deleted tag, round, and combo-decision ids (`{key}:deleted` in browser storage). Reconcile drops
those from the server's copy before merging, and the record is cleared once a save to the server succeeds. So a tag
deleted while the server was off stays deleted.

Remaining limit: the record lives in one browser. If a second browser still holds a copy of a deleted tag, opening
the video there merges it back.

## Tests

```bash
.venv\Scripts\python -m pytest -q tests     # or: npm.cmd run test:api
```

13 tests: CRUD and counts, idempotent registration, save/load round trip in the app's exact JSON shape, PUT
replacing data, per-video id isolation, six kinds of invalid input (each leaves stored data untouched), and data
surviving a server restart. Every test uses its own temporary database.
